# Deploying the Tier 4 Advisor Cockpit to Cloudflare Workers

This guide assumes you have never used Cloudflare before. Follow it in order.

The app is already a Cloudflare Worker: it uses Cloudflare D1 for storage, `cloudflare:workers`
bindings for configuration, and `@cloudflare/vite-plugin` for the build. Moving it off OpenAI Sites
onto your own Cloudflare account is a configuration change, not a port.

**The one thing you must not skip:** on OpenAI Sites, the advisor's identity arrives in a header
that Sites injects and that visitors cannot forge. Off Sites, that header never arrives. Read
[Step 6](#step-6--put-cloudflare-access-in-front-of-the-worker) and
[the warning](#the-warning-you-must-not-skip) before you put any client data in.

---

## What you need

- A Cloudflare account (the free plan is enough to start).
- Node.js 22.13 or newer, and this repository checked out with `npm install` already run.
- A domain in your Cloudflare account. Not strictly required to deploy, but required for
  Cloudflare Access, which is required to run this app safely. If you do not have one yet, you can
  add a domain to Cloudflare later and redeploy.

Everything below uses `npx wrangler`, the Cloudflare CLI, which is already a dev dependency of this
repository. The first command you run will open a browser to log you in:

```bash
npx wrangler login
```

---

## Step 0 — understand the two config files

| File | What it is |
| --- | --- |
| `wrangler.jsonc` | The deployment config you edit. Read its comments; they explain each block. |
| `dist/server/wrangler.json` | Generated by `npm run build`. Do not edit. |

`npm run build` also writes `.wrangler/deploy/config.json`, which makes a bare `npx wrangler deploy`
use the *generated* config — and that one contains a placeholder database id, not yours. So every
deploy command in this guide passes `-c wrangler.jsonc -e production` explicitly. If you forget the
flags you will deploy a Worker with a D1 binding pointing at nothing.

For the same reason, everything real in `wrangler.jsonc` lives under `env.production` rather than at
the top of the file. The local dev server (`npm run dev`) auto-discovers a root `wrangler.jsonc` and
merges it with its own bindings, and a top-level `d1_databases` block would give local development a
second, conflicting database. **When you paste new configuration into `wrangler.jsonc`, paste it
inside `env.production`.**

---

## Step 1 — create the D1 database

D1 is Cloudflare's SQLite database. Create one:

```bash
npx wrangler d1 create tier4-advisor-cockpit
```

The command prints a block of configuration containing a `database_id` (a uuid). Copy that uuid into
`wrangler.jsonc`, replacing `REPLACE_ME_WITH_THE_D1_DATABASE_ID` inside `env.production` →
`d1_databases`.

Do not rename the binding. `DB` is what `db/index.ts` reads and what `.openai/hosting.json`
declares; changing it breaks every query.

Check it worked:

```bash
npx wrangler d1 list
```

---

## Step 2 — create the tables

The repository has SQL migrations in `drizzle/`. Run them in numeric order against the *remote*
database you just created:

```bash
npx wrangler d1 execute tier4-advisor-cockpit --remote --file=./drizzle/0000_tier4_advisor.sql
npx wrangler d1 execute tier4-advisor-cockpit --remote --file=./drizzle/0001_tenancy.sql
npx wrangler d1 execute tier4-advisor-cockpit --remote --file=./drizzle/0002_contact_role.sql
```

`--remote` matters. Without it, Wrangler writes to a local sqlite file on your machine and the
deployed Worker sees nothing.

Two things to know:

- **The app also repairs its own schema on boot.** `ensureDatabase()` in `lib/store.ts` runs
  `CREATE TABLE IF NOT EXISTS` for every table, adds any missing column through a
  `PRAGMA table_info`-guarded `ALTER TABLE`, and creates the indexes. If you skip this step
  entirely, the first request to the deployed app will build the schema for you. Running the
  migrations first is still the cleaner path, because it means the first real request is not also a
  schema migration.
- **`0001` and `0002` are plain `ALTER TABLE ADD COLUMN` statements**, and SQLite has no
  `IF NOT EXISTS` for those. Against a brand-new empty database they apply cleanly. Against a
  database the app has already booted against, they fail with `duplicate column name` — which is
  expected and harmless, because `ensureDatabase()` already added those columns.

Verify:

```bash
npx wrangler d1 execute tier4-advisor-cockpit --remote --command="SELECT name FROM sqlite_master WHERE type='table'"
```

You should see `engagements`, `artifacts`, `transcripts`, `activities` and `intents`.

### Moving existing data off OpenAI Sites

If you have live engagements on the Sites deployment, they live in a D1 database inside that
hosting environment. Whether you can export it with `npx wrangler d1 export` depends on whether that
database sits in a Cloudflare account you control — if it was provisioned by the Sites control
plane, it may not be listed by `npx wrangler d1 list` under your login. Check that first, and if it
is not reachable, ask the host how to obtain an export before you decommission the Sites deployment.
When you do have an export, `npx wrangler d1 execute <database> --remote --file=<export>.sql` loads
it into the new database. Read [Step 5](#step-5--set-configuration-and-secrets) about
`LEGACY_OWNER_EMAIL` **before** you import anything, because the ownership backfill runs once.

## Step 3 — build

```bash
npm run build
```

This produces `dist/server/` (the Worker) and `dist/client/` (static assets). `wrangler.jsonc`
points at both. Rebuild before every deploy.

## Step 4 — deploy

```bash
npx wrangler deploy -c wrangler.jsonc -e production
```

Wrangler prints the bindings it attached — you should see `env.DB`, `env.ASSETS` and `env.IMAGES` —
and then the URL it deployed to, `https://tier4-advisor-cockpit.<your-subdomain>.workers.dev`.

To check the configuration without deploying anything, add `--dry-run`:

```bash
npx wrangler deploy --dry-run -c wrangler.jsonc -e production
```

At this point the app is live **and unprotected**. Do not enter client data yet. Continue to
Step 5 and Step 6.

> If `wrangler deploy` rejects the `images` binding because your account does not have Cloudflare
> Images enabled, delete the `"images"` block from `wrangler.jsonc` and redeploy. Only the
> `/_vinext/image` optimizer uses it.

## Step 5 — set configuration and secrets

Nothing secret is committed to this repository. Each value is set on the deployed Worker with:

```bash
npx wrangler secret put <NAME> -c wrangler.jsonc -e production
```

The command prompts for the value and does not echo it. Re-running it replaces the value. Changes
take effect on the next request; you do not need to redeploy. `npx wrangler secret list -c
wrangler.jsonc -e production` shows which names are set (never the values).

### Identity and tenancy — set these first

| Variable | What it unlocks | Optional? |
| --- | --- | --- |
| `REQUIRE_ADVISOR_AUTH` | Set to `1`. Disables the unauthenticated fallback, so a request with no verified identity is refused instead of being treated as the single local advisor. | **Required** on any deployment more than one person can reach |
| `CF_ACCESS_TEAM_DOMAIN` | Your Zero Trust team domain, e.g. `yourteam.cloudflareaccess.com`. Tells the app where to fetch Cloudflare Access's signing keys. | Required for Access (Step 6) |
| `CF_ACCESS_AUD` | The Access application's AUD tag. The app rejects any token issued for a different application. | Required for Access (Step 6) |
| `LEGACY_OWNER_EMAIL` | The advisor who owns rows created before per-advisor tenancy existed. See the ordering note below. | Optional; defaults to `LOCAL_ADVISOR_EMAIL` |
| `LOCAL_ADVISOR_EMAIL` | The single fallback advisor identity. Meaningful only when `REQUIRE_ADVISOR_AUTH` is unset — which is a local-development configuration, not a production one. | Optional; do not rely on it in production |

### Optional integrations

The whole deterministic workflow runs with none of these. Add only what you intend to use.

| Variable | What it unlocks |
| --- | --- |
| `OPENAI_API_KEY` | OpenAI Responses API web research. Without it, research falls back to deterministic website extraction. |
| `OPENAI_RESEARCH_MODEL` | Overrides the research model. Defaults to `gpt-5.6-sol`. |
| `OPENAI_TRANSCRIPT_MODEL` | Overrides the transcript-synthesis model. Falls back to `OPENAI_RESEARCH_MODEL`; with no key at all, synthesis stays deterministic and the UI says so. |
| `FIREFLIES_API_KEY` | Server-side Fireflies transcript import. |
| `RESEND_API_KEY` | The email sender used for an approved readiness-brief send intent. |
| `EMAIL_FROM`, `EMAIL_REPLY_TO` | Sender identities for that adapter. Needed alongside `RESEND_API_KEY`. |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`, `GOOGLE_REFRESH_TOKEN` | Server-side Google access for the Sheets and Docs adapters. All four are needed together. |
| `GOOGLE_SHEETS_ID` | The CRM workbook an approved write-back intent appends to. |
| `GOOGLE_DRIVE_ROOT_FOLDER_ID` | Destination folder for approved Drive/Docs artifacts. |
| `APOLLO_API_KEY` | Reserved. No direct adapter is implemented; setting it only changes what `/api/integrations` reports. |
| `PANDADOC_API_KEY`, `PANDADOC_TEMPLATE_UUID` | Reserved, as above. |

`.env.example` is the authoritative list for local development; every name in it is settable here.
Values that are not secret — `OPENAI_RESEARCH_MODEL`, `GOOGLE_SHEETS_ID` — can instead go in a
`"vars": { ... }` block inside `env.production` in `wrangler.jsonc` if you would rather see them in
version control. Never put a key, token, or client secret there.

### `LEGACY_OWNER_EMAIL` and the first-boot backfill — ordering matters

Every row in the database carries an `owner_id`, and every query is scoped to it in SQL. Rows
written before that column existed have an empty owner and would be invisible to everyone.

`ensureDatabase()` handles this exactly once: the first time it adds the `owner_id` column to a
table that already has rows, it claims every ownerless row for `LEGACY_OWNER_EMAIL` (falling back to
`LOCAL_ADVISOR_EMAIL`). It does not run again afterwards.

So:

1. Set `LEGACY_OWNER_EMAIL` to the real advisor's address **before** the first request reaches a
   database that contains pre-tenancy rows — that is, before importing an export from the Sites
   deployment, and before enabling `REQUIRE_ADVISOR_AUTH`.
2. If you get the order wrong, those rows are claimed by the local fallback identity instead and you
   will have to re-assign `owner_id` by hand with `wrangler d1 execute`.

On a brand-new empty database there is nothing to backfill and this variable does not matter.

## Step 6 — put Cloudflare Access in front of the Worker

Cloudflare Access (part of Zero Trust) is the identity provider that replaces the OpenAI Sites
login. It sits in front of the Worker, makes the visitor sign in with Google (or Okta, or a one-time
PIN), and then forwards the request with two extra headers:

- `Cf-Access-Authenticated-User-Email` — plain text, and worthless on its own;
- `Cf-Access-Jwt-Assertion` — a signed token only Access can produce.

`lib/access-jwt.ts` verifies that signature against your team's published keys and checks the
issuer, audience and expiry. The app trusts the signed token, never the plain header.

### 6a. Migrate the API routes to the async resolver first

**Do this before setting `CF_ACCESS_TEAM_DOMAIN` and `CF_ACCESS_AUD`.**

Verifying a signature requires a network fetch, so it cannot be done synchronously. `lib/auth.ts`
exposes `resolvePrincipalAsync` / `requirePrincipalAsync` for it, alongside the original synchronous
`resolvePrincipal` / `requirePrincipal`, which deliberately ignore the Access header rather than
trust it unverified.

The API routes under `app/api/` still call the synchronous versions. Until they are switched over,
a deployment with `CF_ACCESS_*` set and `REQUIRE_ADVISOR_AUTH=1` answers **401 to every API
request** — the safe failure, but a broken app. Switch the routes to `requirePrincipalAsync`
(`const principal = await requirePrincipalAsync(request);`) first, then continue.

### 6b. Serve the app from a domain you own

Access protects hostnames on a zone in your Cloudflare account. It cannot be applied to a
`*.workers.dev` URL. So before you can protect the app you need it on a real domain:

1. Add your domain to Cloudflare (dashboard → *Add a site*) if it is not there already.
2. In `wrangler.jsonc`, inside `env.production`, set `"workers_dev": false` and add a route:

   ```jsonc
   "routes": [{ "pattern": "cockpit.example.com", "custom_domain": true }]
   ```

3. Redeploy: `npm run build && npx wrangler deploy -c wrangler.jsonc -e production`.

Turning `workers_dev` off is not cosmetic. A `workers.dev` URL that stays enabled is a second door
into the same Worker that Access never sees. The app fails closed on that door once `CF_ACCESS_*`
are set — no verified assertion, no principal, 401 — but do not leave it open.

### 6c. Create the Zero Trust team and a Google login method

In the Cloudflare dashboard, open **Zero Trust**. The first time, it asks you to choose a *team
name*; that name becomes your **team domain**, `<team-name>.cloudflareaccess.com`. If you have
already done this, the team domain is shown in Zero Trust → **Settings** → **Custom Pages** /
**General**, wherever your dashboard version puts it — it is the only `*.cloudflareaccess.com`
hostname in there. That value is what `CF_ACCESS_TEAM_DOMAIN` needs.

Then add Google as a login method: Zero Trust → **Settings** → **Authentication** → **Login
methods** → add Google. This asks for a Google OAuth client id and secret, which you create in the
Google Cloud Console under *APIs & Services → Credentials*; the authorized redirect URI Google needs
is the callback URL Cloudflare shows you on that same screen (it is under your team domain, at
`/cdn-cgi/access/callback`). Cloudflare's setup panel states the exact value — copy it from there
rather than typing it from memory. Use the **Test** button Cloudflare provides before moving on.

### 6d. Create the Access application and its policy

Zero Trust → **Access** → **Applications** → **Add an application** → **Self-hosted**.

- **Application domain:** the hostname from 6b, e.g. `cockpit.example.com`. Leave the path empty so
  the whole app is protected.
- **Policy:** one policy, action **Allow**. Add an include rule listing who may sign in: either
  *Emails* with each advisor's address, or *Emails ending in* `@yourcompany.com` if every advisor is
  on your domain. Anything not matched by an Allow policy is refused by Cloudflare before the
  request ever reaches the Worker.
- **Login methods:** restrict the application to the Google login method you configured, so a
  one-time PIN cannot be used as a side door.

After saving, open the application again. Its **Application Audience (AUD) Tag** is a long hex
string shown on the application's overview/settings page. That value is what `CF_ACCESS_AUD` needs.
It is not a secret in the cryptographic sense, but it is deployment-specific — it is what stops a
token minted for some *other* Access application in your account from being accepted here.

### 6e. Turn it on

```bash
npx wrangler secret put CF_ACCESS_TEAM_DOMAIN -c wrangler.jsonc -e production   # yourteam.cloudflareaccess.com
npx wrangler secret put CF_ACCESS_AUD -c wrangler.jsonc -e production           # the AUD tag
npx wrangler secret put REQUIRE_ADVISOR_AUTH -c wrangler.jsonc -e production    # 1
```

Then check it:

1. Open the app in a private browser window. You should be redirected to a Cloudflare sign-in page,
   not to the app.
2. Sign in with an allowed Google account. You should land in the cockpit.
3. Sign in with an account that is *not* in the policy. Cloudflare should refuse you.
4. `GET /api/me` (while signed in) should return your email as the principal.

`GET /api/integrations` reports which identity source is actually in force —
`advisorAuthMode()` in `lib/auth.ts` returns `cloudflare-access`, `sites-headers`, `local-fallback`
or `denied`. If it says anything other than `cloudflare-access` after this step, one of the two
`CF_ACCESS_*` values is missing or misspelled. (`denied` specifically means exactly one of them is
set while `REQUIRE_ADVISOR_AUTH` is on: the app refuses everything rather than quietly falling back
to trusting a header.)

## The warning you must not skip

**If you deploy this app to Cloudflare without Cloudflare Access and without
`REQUIRE_ADVISOR_AUTH`, then anyone who has the URL is treated as the single local advisor and can
read, edit and export every engagement in the database.**

There is no login screen inside this application. It has never had one. On OpenAI Sites the login
belongs to Sites, which injects an identity header that the app trusts. Off Sites that header never
arrives, so:

- with `REQUIRE_ADVISOR_AUTH` unset, every visitor silently resolves to `LOCAL_ADVISOR_EMAIL` — one
  shared identity, and it owns every record;
- with `REQUIRE_ADVISOR_AUTH=1` but no Access configured, nobody can authenticate at all and every
  API call returns 401.

Neither is a usable production state. Cloudflare Access is what makes the deployment safe. Until
Step 6 is finished, treat the deployment as a scratch environment and keep real client data out of
it.

One more consequence, since the `oai-authenticated-user-email` header is trusted whenever Access is
not configured: on any host that is *not* OpenAI Sites, a visitor can simply send that header
themselves and become whichever advisor they name. That is safe on Sites, which strips inbound
copies of it, and only there. It is another reason `CF_ACCESS_*` must be set before the app is
exposed.

dashboard under the Worker. The application does not log tokens, keys, or transcript content.

## A note on Vercel

Vercel is a port, not a configuration change. The app depends on three Cloudflare-specific things:

- **D1.** `db/index.ts` and `lib/store.ts` speak the D1 API directly (`prepare`/`bind`/`batch`).
  On Vercel you would replace it with Postgres or similar and rewrite that layer plus the
  `drizzle/` migrations.
- **`cloudflare:workers` bindings.** `lib/auth.ts`, `lib/store.ts` and the integration adapters read
  configuration from the `env` object imported from `cloudflare:workers`. That module does not exist
  off Workers; every read would move to `process.env`.
- **The Worker build.** `vite.config.ts` builds through `@cloudflare/vite-plugin` into a Worker
  entry (`worker/index.ts`), and `dist/server/index.js` is a Workers module, not a Node server.

The Cloudflare Access work in `lib/access-jwt.ts` would also not apply; Vercel deployments would
need their own identity provider in front of the app, and the same warning above would apply until
one existed. Cloudflare Workers is the low-friction target precisely because none of this has to
change.
